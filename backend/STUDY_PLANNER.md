# Study Planner V1 backend

Study sessions are independent scheduled study blocks. The frontend, Tasks and AI integrations are unchanged. No calendar model, relationships, DELETE endpoint, recurrence or reminders are included.

## Files and data

- `app/models/study_session.py`: `StudySession` uses the existing SQLAlchemy Base and the `study_sessions` table. It stores integer `id`, required `title`/`category` (255 characters), optional text `description`, required timezone-aware `start_time`/`end_time`, `status` (default `Planned`), and automatic `created_at`/`updated_at` timestamps.
- `app/schemas/study_session.py`: Pydantic v2 create, partial update and response schemas. Status accepts exactly `Planned`, `Completed`, or `Skipped`. Title and category are trimmed and cannot be blank. Unknown fields and client-supplied IDs/timestamps are rejected. Only description can explicitly be null.
- `app/routers/study_sessions.py`: GET list/detail, POST (201), and PATCH. Missing IDs return 404. Invalid input returns 422. Lists sort by start time ascending, then ID ascending for stable ties.
- `app/models/__init__.py`, `alembic/env.py`, `app/main.py`: register model metadata and the router while preserving existing endpoints.
- `alembic/versions/cbfc69511070_create_study_sessions_table.py`: migration following `022419ef08e9`.
- `tests/test_study_sessions.py`: HTTP tests against migrated PostgreSQL, with records rolled back.

## Validation and timestamps

Every created session must have `end_time > start_time`. Equal or reversed intervals return 422.

PATCH locks the existing row, merges only supplied fields with the stored values, and validates that complete result through `StudySessionCreate` before changing any ORM fields. This catches a start-only update that exceeds the existing end, and an end-only update that precedes the existing start. Moving both boundaries together is allowed when their final interval is valid. Rejected updates leave all stored fields and timestamps unchanged.

`created_at` and `updated_at` are populated by PostgreSQL when created. Every successful PATCH explicitly advances `updated_at` using `clock_timestamp()`, including empty or unchanged payloads. `created_at` is preserved.

## Timezones

This follows the existing Tasks convention: an input without an offset is interpreted as UTC without changing its clock fields. Thus `2026-09-28T18:00:00` means `2026-09-28T18:00:00Z`, not browser-local time. For 18:00 Sri Lanka time, send `2026-09-28T18:00:00+05:30`. PostgreSQL preserves the instant; responses may represent it with a different offset. Comparisons use instants, including when the two inputs have different offsets.

## Migration and preservation

The autogenerated migration was inspected before applying. Its upgrade creates only `study_sessions`; Alembic also advances its revision marker. It does not alter any existing data tables. `Base.metadata.create_all()` is not used.

Applied with `.\.venv\Scripts\python.exe -m alembic upgrade head`. Existing counts and content fingerprints matched before and after: certifications 3, courses 2, CTF challenges 3, labs 4, notes 3, projects 3, tasks 2, topics 3. `alembic check` reported no pending model changes. Downgrading this migration would drop `study_sessions`.

## Swagger walkthrough

From the project root in PowerShell, start the backend if it is not already running:

```powershell
cd backend
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

1. Open http://127.0.0.1:8000/docs.
2. Expand GET `/api/db-health`, select **Try it out**, then **Execute**. Expect 200 and `{"database":"connected"}`.
3. Under **Study Sessions**, execute GET `/api/study-sessions`. Expect 200 and a list (initially empty).
4. Execute POST `/api/study-sessions` with this body:

```json
{
  "title": "VLSM Practice",
  "category": "Networking",
  "description": "Practice VLSM subnetting questions.",
  "start_time": "2026-09-28T18:00:00",
  "end_time": "2026-09-28T19:00:00",
  "status": "Planned"
}
```

5. Expect 201. Copy the returned `id`. Confirm automatic timestamps and `Planned` status. GET `/api/study-sessions/{session_id}` with that ID should return the same session.
6. PATCH that ID with `{"start_time":"2026-09-28T20:00:00"}`. Expect 422 because the existing end is 19:00. GET again to confirm no fields or timestamps changed.
7. PATCH with `{"end_time":"2026-09-28T18:00:00"}`. Expect 422 for equal times.
8. PATCH with `{"start_time":"2026-09-28T20:00:00","end_time":"2026-09-28T21:00:00"}`. Expect 200 and updated times.
9. PATCH with `{"status":"Completed"}`, then `{"status":"Skipped"}`. Both should return 200. `{"status":"Done"}` should return 422.
10. PATCH with `{"description":null}` to clear the description. PATCH with `{}` and confirm `updated_at` advances while `created_at` remains unchanged.
11. Create another session with an earlier start time. GET the list and confirm chronological ordering, regardless of status.
12. GET and PATCH session ID `-1` (PATCH body `{}`) should return 404. POST with equal/reversed start and end times should return 422.
13. Execute existing GET endpoints `/api/courses`, `/api/labs`, `/api/notes`, `/api/projects`, `/api/certifications`, `/api/ctf`, and `/api/tasks`. Expect 200 with their existing data.

Swagger writes real persistent sessions. The automated tests instead roll back their test records:

```powershell
cd backend
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Verification result: all 58 backend tests passed, including six Study Sessions test cases. Existing record fingerprints also matched after testing, and the study_sessions table remained empty.
