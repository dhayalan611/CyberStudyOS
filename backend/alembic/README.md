# Database migrations

Run commands from `backend` using its virtual environment. `env.py` loads
`app.config.settings.DATABASE_URL`, including `backend/.env`, and imports all
models into `Base.metadata`. Credentials do not belong in `alembic.ini`.

## Existing development database

The existing `courses` and `topics` tables were inspected and matched to revision
`0001`. They are adopted with `python -m alembic stamp 0001`, which only creates
and writes the `alembic_version` tracking table; it does not execute `upgrade()`.
This project database has already been stamped. Do not stamp again as a way to
skip future migrations. Before adopting any other existing database, inspect its
schema and verify it matches the baseline, including defaults, foreign keys,
and indexes. Never run the initial creation migration against existing tables.

## Fresh empty database

After configuring DATABASE_URL for an empty database:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
```

This applies the full migration chain for courses, topics, labs, notes, projects,
certifications, CTF challenges, tasks, and study sessions, including their
indexes/constraints and the Alembic version record.
Application startup no longer creates or modifies tables.

## Labs migration

Revision `0002` follows `0001`. Its upgrade only creates the `labs` table;
it does not alter courses or topics. The autogenerated migration and offline
SQL were reviewed before applying it to the existing database. Alembic also
updates its revision record. Its downgrade drops only `labs` (and its data).
See [Labs testing instructions](../LABS.md) for API verification.

## Future model changes

```powershell
.\.venv\Scripts\python.exe -m alembic revision --autogenerate -m "describe schema change"
# Review the generated upgrade/downgrade operations before proceeding.
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic check
```

Autogenerate compares the connected database with model metadata and writes a
candidate migration; it does not apply it. Review it carefully, especially any
drop operations or renames. `upgrade head` applies pending upgrade operations
in revision order. Back up valuable data before schema-changing migrations.
`check` reports model/schema drift without generating a revision.

The initial baseline deliberately refuses downgrade to base, since that would
drop development data. Future migrations should define their own appropriate
downgrade behavior. `create_all()` is not a migration system: it creates missing
tables but does not evolve existing table definitions or track schema versions.
